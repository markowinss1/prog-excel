# Архитектура Excel Freelancer Toolkit — этапы 1, 2A и 2B

Цель — локальное приложение с предпросмотром, независимым Cleaner и безопасным GUI-сценарием.
Чтение отделено от Qt, чистые преобразования — от файлового ввода-вывода.
Контейнер DI, реестр плагинов, фабрики и абстрактные базовые классы не нужны.

Все Python-пакеты содержат `__init__.py`. `src` исключает случайный импорт
неустановленного пакета из корня проекта. `modules/cleaner` не импортирует Qt,
openpyxl или файловые адаптеры и переиспользует `application.models.Cell`.
Для Merger/Compare каталоги не создаются.

## Слои и зависимости

| Слой | Ответственность | Зависимости |
| --- | --- | --- |
| UI | Диалоги, параметры, вкладки, отчёт, ошибки, жизненный цикл Qt | Application, CleaningPlan из Modules, PySide6 |
| Application | Сценарии предпросмотра, анализа и экспорта через контракты | Стандартная библиотека, Modules для сценария Cleaner |
| Infrastructure | Файлы, профиль безопасности XLSX, атомарный экспорт | Application, модели Modules, openpyxl, csv, ZIP/XML |
| Modules | Чистые преобразования, настройки, результат, отчёт | Только стандартная библиотека и существующая Cell из application.models |

`PreviewReader` — маленький структурный `Protocol`, а не иерархия наследования.
Он уже полезен: тесты Application и фоновой работы подставляют читатель без файловой
системы. `__main__` явно собирает `FilePreviewReader → PreviewService` и
`FileCleaningStorage → CleaningService`, передавая оба сервиса в `MainWindow`.
Для совместимости предпросмотр можно создать без CleaningService, тогда анализ недоступен.
UI не импортирует openpyxl/csv и не открывает файлы. Путь — только аргумент запроса.

## Поток данных и потоки Qt

```text
GUI-поток: выбор файла / листа / повторная загрузка
    → PreviewWorker (наследует ServiceWorker)
    → PreviewService.load() → ограниченный Preview

GUI-поток: Analyze & Clean
    → неизменяемые path, sheet, CsvOptions, CleaningPlan из checkbox
    → ServiceWorker → CleaningService.analyze() → CleaningJob
    → job.previews() → два ограниченных Preview исходного снимка/результата

GUI-поток: Save Cleaned File
    → QFileDialog → новый путь исходного формата
    → ServiceWorker → CleaningService.export(job, destination)
    → успешный путь или ошибка

Во всех случаях: queued loaded / failed → GUI-слоты окна
                  queued finished → освобождение worker, восстановление контролов
```

`ServiceWorker` расширяет существующий подход QThread, выполняя один синхронный вызов.
`PreviewWorker` остаётся тонкой обёрткой с кооперативной отменой чтения. Анализ и экспорт
используют тот же класс, слот ошибок, индикатор и жизненный цикл; второго пула потоков нет.
Задачи получают сервисы и снимки аргументов, а не виджеты. Подготовка bounded previews
тоже выполняется в worker: сканирование ширины полной таблицы не переносится в GUI.

Все виджеты и модели меняются только в GUI-потоке. Подключения сигналов явно queued,
слоты окна помечены `Slot`. Ожидаемые `PreviewError` / `CleaningError` выводятся целиком;
неожиданные исключения журналируются, пользователь получает понятное сообщение.
Ошибка экспорта не отправляет сигнал успеха; предыдущая надпись о сохранении очищается
при новой попытке. Полная ошибка доступна в read-only поле с прокруткой.

Одна ссылка `_worker` разрешает только одну задачу: загрузку, анализ или экспорт.
На время работы выбор файла, параметры и кнопки запуска заблокированы. Индикатор
неопределённый (0…0); фиктивных процентов и кнопки отмены Cleaner нет.
Ссылка хранится до `finished`, затем вызывается `deleteLater`.

Закрытие занятого окна устанавливает `_closing` и откладывается до `finished`.
Для предпросмотра запрашивается реальная кооперативная отмена; для анализа/экспорта
ожидается нормальное завершение. `terminate()`, блокирующий GUI `wait()` и фиктивная
отмена не используются. Экспорт, начатый до закрытия, может создать файл до закрытия
окна. Поздние результаты не обновляют интерфейс закрывающегося окна.

## Состояние Cleaner в GUI

Четыре checkbox изначально включены; GUI передаёт их в существующий `CleaningPlan`.
Дефолты самого Python API остаются выключенными. Заголовок, выбор столбцов и порядок
операций сохраняют настройки движка; повторной реализации очистки в UI нет.

После успеха окно хранит `CleaningJob`; `job.previews()` ограничивает отображение
100 строками и 200 столбцами, не изменяя полные таблицы. Обе вкладки строятся из
одного снимка анализа. До анализа Original Data использует обычный PreviewService.
`Cleaning Summary` отображает поля `CleaningReport` напрямую, без пересчёта метрик
по видимым строкам. Предупреждения и выполненные операции берутся из того же отчёта.

Смена выбранного файла, листа, кодировки, разделителя, checkbox или повторная загрузка
удаляет job, очищает отчёт/Cleaned Data и блокирует экспорт. При изменении параметров
источника очищается и исходный предпросмотр, чтобы не выдавать его за актуальный.
Счётчик ревизий дополнительно не позволяет устаревшему фоновому результату вернуть
доступ к экспорту после программного изменения контролов. Отмена файлового диалога
не меняет действующий job. Неуспешный повторный анализ не возвращает старый результат.

При ошибке анализа оригинальный предпросмотр сохраняется, экспорт недоступен.
При ошибке экспорта рассчитанный job остаётся пригодным для повторной попытки с новым
именем. Внешние изменения файлов автоматически не отслеживаются: действует контракт
снимка этапа 2A; новое содержимое требует повторного анализа.

Диалог сохранения предлагает `_cleaned` и только исходный формат. У пути без расширения
добавляется расширение источника. Диалог не предлагает разрешить перезапись: запрет
оригинала/занятого пути остаётся в существующем FileCleaningStorage. Успешный путь
показывается полностью. В интерфейсе CSV есть подсказка о текстовом импорте ID в Calc.

## Контракт предпросмотра и сохранность данных

`Preview` содержит путь, кортежи строк/ячеек, листы, выбранный лист, признаки продолжения
и фактические настройки CSV. Dataclass заморожены, контейнеры неизменяемы.
`Cell` сохраняет значение, тип openpyxl и числовой формат; у CSV значение всегда строковое.
`None`, пустая строка, число, bool и формула не сводятся к единому строковому
представлению в модели. Только UI преобразует значение в текст для показа.

Первая строка не интерпретируется как заголовок. Пустые строки и ведущие нули не удаляются.
Предпросмотр содержит до 100 строк и 200 столбцов; 101-я строка нужна для признака продолжения.
Лимит столбцов касается данных, передаваемых в GUI; один CSV-record / XML-row может быть шире.
Файлы с меньшим числом строк не дополняются искусственными строками.

XLSX: `read_only=True`, `data_only=False`, `keep_links=False`, обязательное закрытие
книги и внешнего дескриптора. Формулы остаются текстом, внешние ссылки не загружаются
по сети. `reset_dimensions()` позволяет читать файлы с неверными метаданными диапазона.
Книга никогда не сохраняется адаптером. Это не гарантия побитового воспроизведения
книги при экспорте: для него реализован отдельный контракт Cleaner, описанный ниже.

CSV: `newline=""`, строгий декодер и `csv.reader(strict=True)`, без `QUOTE_NONNUMERIC`.
UTF-8-sig читает UTF-8 с BOM и без; Windows-1251/1252 и UTF-16 выбираются явно.
Sniffer исследует ограниченный образец, допустимы четыре разделителя.
Ошибки эвристики решаются ручным выбором; кодировка автоматически не угадывается.

Известные ошибки формата/IO переводятся в `PreviewError`. Ошибка декодирования
объясняет, как повторить загрузку. Неожиданная ошибка перехватывается на границе
worker: GUI получает сообщение, traceback остаётся в журнале терминала.
Предпросмотр не заменяет валидацию полного файла перед обработкой и экспортом.

## Cleaner: контракты и поток обработки

Минимальное расширение существующей архитектуры: `Cell` и `CsvOptions` переиспользуются;
`Preview` остаётся ограниченной моделью отображения. `Table` представляет полные данные
как неизменяемые кортежи строк из `Cell`. Типы не выводятся из текста. XLSX-адаптер отклоняет неоднозначное декодирование
чисел/дат, если разные исходные значения становятся одинаковыми значениями Python:
такая таблица могла бы дать ложные дубликаты. Для чистого API
формула явно помечается `data_type="f"`; входные списки строк преобразуются в кортежи.

```text
Python API / GUI
    → CleaningService.analyze(path, plan, sheet, csv_options)
    → CleaningStorage.read() → CleaningSource (Table + сведения об оригинале)
    → modules.cleaner.clean(Table, CleaningPlan) → CleaningResult
    → проверка безопасности результата для всей книги
    → CleaningJob(source, result) → report / result.preview(limit)

Явный экспорт
    → CleaningService.export(job, new_path)
    → повторная проверка соответствия строк результата источнику
    → сериализация во временный файл + flush/fsync
    → os.link(temp, destination), без замены существующего пути
    → удаление временного файла
```

`CleaningStorage` — один небольшой структурный Protocol, без реестра плагинов.
`FileCleaningStorage` реализует чтение, проверку и запись. Сценарий не содержит Qt
и вызывается из рабочего потока GUI. Исключения формата/IO преобразуются
в `CleaningError`; неподдерживаемые возможности дают явную ошибку до записи.

`clean(table, plan)` ничего не записывает и не меняет вход. Операции выполняются
в фиксированном порядке: **Trim → Empty Rows → Duplicates → Missing Values**.
План содержит независимые выключенные по умолчанию флаги, `has_header=True`,
необязательный `duplicate_columns` и `missing_detail_limit=1000`.
Изменение прежнего плана архитектуры намеренное: произвольный порядок не предоставляется,
поскольку порядок меняет результат. Сравнение дубликатов использует тип Cell,
точный Python-тип и значение; стили в ключ не входят. Первое вхождение сохраняется.

Заголовок не удаляется и не входит в ключи дубликатов, но Trim и поиск пропусков
обрабатывают его. Входной прямоугольник задаёт ширину поиска пропусков. В XLSX его
нижняя/правая граница определяется по XML ячеек со значениями/формулами, независимо
от `dimension` и удалённого оформления. CSV сохраняет длины исходных записей.
Числа строк отчёта включают заголовок; счётчик Trim учитывает и последующие удаления.

`CleaningResult` содержит `table`, `report`, `source_rows` (нумерация с 1).
`CleaningReport` включает исходные/итоговые строки, удалённые пустые строки/дубликаты,
изменённые ячейки, полный счётчик пропусков, ограниченный список `MissingValue`,
признак усечения, предупреждения и выполненные операции. У проблемы есть координаты
в результате и номер исходной строки. `preview(limit)` создаёт небольшой срез
**готового** результата; он не предназначен для дешёвого открытия большого файла.
Для первичного предпросмотра сохраняется `PreviewService` с ограниченным чтением.

## Профиль безопасности и экспорт XLSX

Универсальное сохранение Excel через openpyxl не обещается. Адаптер читает исходный
XLSX в неизменяемый снимок байтов, проверяет ZIP-части, связи и XML всех листов.
Допускаются только части обычной табличной книги и известные базовые элементы.
Значения читает openpyxl в read-only/data_only=False; оригинал никогда не сохраняется им.

Экспорт меняет XML только выбранного листа: Trim переводит изменённые текстовые
ячейки в inline strings, сохраняя стиль; удаление строк переносит координаты ячеек
и свойства сохранившихся строк. Строки с оформлением за областью данных также
сдвигаются. Остальные части ZIP, включая другие листы, styles и shared strings,
сохраняют исходное несжатое содержимое. Устаревший `dimension` выбранного листа
удаляется. При отсутствии изменений сохраняются байты всех частей.

Все формулы проверяются до обработки. Если требуется фактическое удаление строк
и формула есть на любом листе, операция отклоняется. Trim/анализ обычных формул
допустимы, формулы и кэш остаются неизменными; пересчёт не выполняется. Отчёт
предупреждает о возможном устаревании кэша после изменения зависимых значений.
Текст `=...` сохраняет строковый тип и не превращается в формулу.

Объединения, Tables, именованные диапазоны, фильтры, split/frozenSplit, группировки,
защита, условное форматирование, validation, rich text, общие/массивные формулы,
внешние связи, комментарии, гиперссылки, рисунки/диаграммы и неизвестные части/расширения
не поддерживаются даже на другом листе. UTF-16 XML, DTD/entities и неоднозначные
OOXML escape-последовательности также отклоняются. Полный список и практические
ограничения приведены в README. Это профиль поддержки, а не полный валидатор OOXML.

Экспорт CSV использует исходные настройки и стандартный writer без преобразования
типов. Ведущие нули сохраняются в файле, но сторонняя программа может сама угадать
числовой тип или интерпретировать формулоподобный текст. Автоматическое добавление
апострофов изменило бы данные, поэтому не применяется. Конвертации CSV/XLSX нет.

Назначение должно быть новым путём с исходным расширением. Исключительное создание
hard link публикует уже полностью записанный файл и не перезаписывает конкурирующий
файл. Проверяются оригинал, существующие файлы и ссылки. При обычном исключении
временный файл удаляется. Нет гарантии очистки после kill/power loss и полной
устойчивости к сбою питания; требуются hard links в файловой системе назначения.
После анализа экспорт использует снимок, не перечитывая изменившийся оригинал.

## XLSX Compatibility

### Где выполняются проверки

В `infrastructure/files/cleaning_xlsx.py`:

- `PART` и `inspect_archive()` проверяют ZIP-каталог, размеры и разрешённые компоненты;
  там же проверяются relationships и соответствие листов их XML-частям.
- `parse_xml()` запрещает DTD/entities и неподдерживаемую кодировку;
  `_check_tags()` применяет `SHEET_TAGS`/`BOOK_TAGS` и ограничения атрибутов.
- `_check_sheet_views()` проверяет вложенность `sheetViews → sheetView → pane/selection`,
  количество элементов, состояние закрепления, координаты и принадлежность области.
- `validate_result()` проверяет отображение исходных строк, изменения ячеек, запрет удаления
  при формулах и возможность сохранить представления после удаления строк.
- `write_xlsx()` редактирует XML выбранного листа и копирует остальные ZIP-компоненты.
  `FileCleaningStorage.write()` повторяет проверку результата и публикует готовый файл
  атомарно, с исключительным созданием нового пути.

Ранее `pane` отсутствовал в `SHEET_TAGS`, а featurePropertyBag не соответствовал `PART`.
Поэтому предпросмотр read-only работал, а полный анализ завершался защитной ошибкой.
Неизвестные части и элементы по-прежнему отклоняются; общая проверка не отключена.

### Закрепления и координаты представлений

Добавлен узкий профиль обычного `state="frozen"`: первая строка, первый столбец,
несколько строк/столбцов, их сочетание. `xSplit` — количество закреплённых столбцов,
`ySplit` — строк. `topLeftCell` задаёт прокрутку незакреплённой области и может находиться
дальше границы. Эти свойства нельзя подменять друг другом. См.
[уточнения Office для pane](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/bb178944-7838-4a58-9c16-e0c63d428a43).

Поддерживается обычный вид слева направо; split/frozenSplit, дробные/отрицательные/нечисловые
смещения, неверные координаты и неизвестные свойства pane/selection отклоняются.
При Trim XML-свойства сохраняются. При отсутствии изменений сохраняются байты всего листа.

Алгоритм при удалении строк выбранного листа:

1. Если удаляемая строка ≤ `ySplit` хотя бы одного представления, отказ: число и состав
   закреплённых строк не меняются автоматически.
2. Для остальных представлений сохраняются `xSplit`, `ySplit`, `activePane` и принадлежность
   `selection.pane`. Координаты сохранившихся строк преобразуются как
   `new_row = old_row − число удалённых строк < old_row` через бинарный поиск.
3. Преобразуются `sheetView.topLeftCell`, `pane.topLeftCell`, `selection.activeCell` и все
   границы диапазонов `sqref`. Порядок диапазонов и `activeCellId` сохраняются.
   Если удаляется сам якорь или любая строка выделенного диапазона, отказ: новая активная
   ячейка и усечение выделения не выбираются эвристически. См.
   [семантику selection](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.selection?view=openxml-3.0.1).
4. Те же правила проверяются на анализе, повторно перед экспортом и применяются к XML
   при записи. На остальных листах ничего не сдвигается; их байты сохраняются.

`inspect_archive()` извлекает небольшой сериализованный `sheetViews` из уже разобранного XML.
`FileCleaningStorage` сохраняет его для выбранного листа в неизменяемом
`CleaningSource.xlsx_sheet_views`. Проверка результата разбирает только этот фрагмент,
а не полный XLSX повторно. Экспорт использует уже необходимый разбор выбранного листа.
Новые правила также защищают координаты выделения/прокрутки представлений без `pane`.
Слои Application и Cleaner не содержат OOXML-логики; модель лишь переносит снимок метаданных.

### featurePropertyBag: причина защитного отказа и путь расширения

По [MS-XLSX §2.1.22](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-xlsx/19ef002a-0b33-45b3-aa01-fcae807602ff)
часть использует Content-Type `application/vnd.ms-excel.featurepropertybag+xml`,
relationship type `http://schemas.microsoft.com/office/2022/11/relationships/FeaturePropertyBag`
и корень `FeaturePropertyBags`. Обычный путь — `xl/featurePropertyBag/featurePropertyBag.xml`.

[Схема §5.36](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-xlsx/9e45d09d-206b-4134-a90e-b5be9c08b2fa)
описывает типизированные пары ключ/значение: строки, числа, bool, массивы, ссылки `bagId`
на другие bags, `rel` на relationships, расширения и дополнительные атрибуты.
Возможны не только явные `.rels`, но и неявные ссылки из стилей:
[`xfComplement`](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-xlsx/d6ffbc21-ef11-4546-9a07-95885e2fd497)
и `DXFComplement`. Типы `XFComplements`, `XFComplement`,
[`XFControls`](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-xlsx/3fc90597-a4e9-49d8-bd0a-896b674ed9b4)
и `Checkbox` участвуют в описании стилей элементов управления в ячейках.
Следовательно, отсутствие внешнего `.rels` само по себе не доказывает независимость метаданных.

Текущий XML/ZIP writer умеет сохранять несжатые байты таких частей, но пока нет валидатора
их семантики, индексов bags и связей со стилями. Нельзя доказать безопасность неизвестного
содержимого только копированием ZIP. Поддержка не включена даже для пустого bag или
известного checkbox-примера; неизвестные/внешние/повреждённые связи также отклоняются.
Обнаружение части или relationship даёт отдельный `CleaningError`; ничего не удаляется.

В локальном эксперименте с openpyxl 3.1.5 реальный ZIP-образец с четырьмя checkbox-bags,
relationship, Content-Type и `xfComplement` был прочитан и пересохранён библиотекой:
компонент и ссылка из стиля исчезли. Это не ограничение используемого surgical writer,
а дополнительная причина не заменять его универсальным `openpyxl.save()`.

Безопасный следующий этап:

1. Получить обезличенные оригинальные файлы и определить конкретный профиль bags.
2. Добавить проверку Content-Type, точного URI relationship, единственности части,
   нормализованных внутренних Target, отсутствия внешних/неизвестных связей и расширений.
3. Проверять типы bags, ключи, значения, диапазоны индексов, `extRef`, `bagExtId`, ссылки
   `rel`, `xfComplement`/`DXFComplement`, соответствие стилям и использующим их ячейкам.
   Одного добавления пути в `PART` недостаточно.
4. Доказать для разрешённых операций независимость метаданных от перенумерации строк
   либо реализовать коррекцию всех зависимостей. При неизвестной зависимости — отказ.
5. Копировать проверенные части, Content Types и relationships без изменений, проверить
   целостность графа после экспорта, побайтовое сохранение и открытие в Excel на реальных
   образцах. Полное пересохранение через openpyxl не использовать.

### Формулы, GUI и проверка сохранности

Формулы на любом листе по-прежнему запрещают удаление строк; Trim сохраняет формулу и
кэш без вычисления с предупреждением. Общие/массивные/табличные формулы не разрешены.
Остальные ограничения сложных Excel-структур перечислены выше и в README.

GUI не изменён: `CleaningError` передаётся через `ServiceWorker.failed`, анализ не создаёт
`CleaningJob`, кнопка экспорта остаётся недоступной, полный текст ошибки показан пользователю.
Регрессии проверяют успешный экспорт с закреплением, отказы pane/featurePropertyBag,
отсутствие ложного сообщения о сохранении и повторный анализ после изменения операций.

Новые тесты используют настоящие маленькие XLSX во временных каталогах: с закреплением
и без, разными областями, прокруткой и несколькими выделениями, формулами/кэшем, типами,
ID и стилями. Проверяются исходный хеш/mtime, байты остальных ZIP-частей, CRC, корректность
XML и внутренних Target/PartName, повторное открытие openpyxl и отсутствие частичного
выходного файла при ошибке записи. Это не полная валидация OOXML по XSD.
Исходные клиентские файлы отсутствуют; до добавления в `tests/fixtures` именно их
совместимость не подтверждена. Ручная проверка в Excel остаётся отдельным шагом.

## Производительность и этап 2B

Движок проходит строки последовательно; хеш-набор дубликатов сохраняет первые
вхождения, а список проблем ограничен независимо от полного счётчика. Кортежи
исходных ячеек переиспользуются, когда это возможно. При удалении XML-строк дочерний
список заменяется один раз, без многократных линейных удалений из большого списка.
Входная/выходная таблицы и снимок XLSX находятся в памяти; неограниченный streaming
не реализован. Ограничения: 2 000 000 ячеек в прямоугольнике, XLSX 128 MiB,
распакованные части 256 MiB, 1000 ZIP-записей. Это ограничения входа, не гарантия
фиксированного пикового потребления памяти.

Сравнение совместимости XLSX (11 октября 2026): Python 3.14.7, openpyxl 3.1.5,
Linux x86_64. `examples/benchmark_xlsx.py` создаёт 10 000 записей × 5 столбцов
и второй лист; результат — 5 001 строка с заголовком, 500 удалённых пустых строк,
4 500 дубликатов. Все четыре операции включены. Генерация и повторное открытие
не входят в замер; анализ и полный атомарный экспорт измеряются отдельно.
Для каждого варианта выполнен один прогрев и пять измерений последовательно,
в одном окружении, без параллельных benchmark-процессов.

| Вариант | Медиана анализа, с | Медиана экспорта, с |
| --- | ---: | ---: |
| До изменений, `8df65df`, без pane | 1,886 | 0,461 |
| После изменений, без pane | 1,918 | 0,465 |
| После изменений, закрепление A2 | 1,934 | 0,466 |

В этом прогоне изменение для обычного файла составило +1,7% / +0,9%; заметного
ухудшения не обнаружено. Диапазоны анализа: 1,855–1,989 с до изменений,
1,891–2,019 с после; экспорта: 0,458–0,470 / 0,460–0,477 с.
Результат зависит от оборудования, нагрузки, сборщика мусора и файлового кэша;
это локальное сравнение с прогретым кэшем, не универсальная гарантия времени.
Прежняя версия отклоняла pane, поэтому для неё нет корректного замера закреплённого файла.

Воспроизведение: на обеих ревизиях запустить тот же `examples/benchmark_xlsx.py`
одним интерпретатором, указав нужный `src` через `PYTHONPATH`, затем для новой версии
добавить `--freeze A2`. `--repeats` задаёт число измерений; JSON содержит все значения.

Этап 2B использует существующий `CleaningService`: UI выбирает флаги, запускает
анализ, показывает результат/отчёт, затем отдельно вызывает экспорт. Точные проценты
прогресса и кооперативная отмена Cleaner остаются будущей работой; GUI использует
неопределённый индикатор и безопасное ожидание. Поддержка сложных XLSX, пересчёт
формул и расширение настроек заголовков/ключей в GUI вне текущего этапа.

## Проверка решений

pytest создаёт файлы в `tmp_path`; хеши и mtime проверяют неизменность оригиналов.
Тесты Qt проверяют доставку обновления в главный поток, работу таймера во время
чтения и завершение при закрытии. Они используют offscreen и не заменяют ручную
проверку оформления и системного диалога в конкретной Wayland/X11-сессии.

Официальные справочники:
[Qt QThread](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QThread.html),
[openpyxl read-only mode](https://openpyxl.readthedocs.io/en/stable/optimized.html),
[Python csv](https://docs.python.org/3/library/csv.html).


Проверки: `python -m pytest`, `ruff check .`, `ruff format --check .`.
Новые тесты проверяют все 16 комбинаций флагов, фиксированный порядок, строгие типы,
Unicode/ведущие нули, повторную обработку, формулы между листами, лимиты отчёта,
пустые/повреждённые файлы, отказы по структурам XLSX, shared strings, стили,
сохранение байтов других частей, CR/многострочный текст, снимок после изменения
оригинала, запрет перезаписи, гонку создания и очистку после ошибки записи.
Воспроизводимые примеры на 30 000 CSV-строк и 20 000 XLSX-дубликатов проверяют
обработку полных таблиц. Исходные тесты предпросмотра и GUI сохранены.


Тесты этапа 2B проверяют реальные GUI → CleaningService → FileCleaningStorage сценарии,
контракт Application с подставным storage, соответствие checkbox и плана, отчёт,
исходный снимок и вкладки, обработку за пределами 100 строк, CSV-настройки и листы XLSX,
диалоги, инвалидирование, ошибки и повторное сохранение. Искусственно задержанные
анализ/экспорт подтверждают работу таймера GUI, запрет повторного запуска и ожидание
при закрытии; отдельный тест отклоняет устаревший результат. Проверяются размеры окна
760×540 и 1100×900 и доступность полного сообщения об ошибке.

Дополнительно выполнена headless-проверка LibreOffice: файлы, экспортированные через
GUI, успешно открыты и преобразованы в ODS; у XLSX сохранены строковые ID и другой лист.
Автоимпорт CSV в Calc преобразовал ID в числа, поэтому README содержит инструкцию
явного текстового импорта. LibreOffice не добавляется в зависимости проекта или
обязательные pytest-проверки. Нативный GUI вручную не проверялся.
